# 会话、任务与作业模型 v1

**状态：提议。**回答三个问题：用户一边等技能生成一边继续对话时，交互如何不被阻塞；什么时候需要新开上下文；旧的生成会话怎么处理。

## 1. 核心思路

生成技能的 LLM 工作不占用任何交互会话。拆成四层，各管各的：

| 层 | 是什么 | 存放 | 生命周期 |
|---|---|---|---|
| 连接 | 设备与 Runtime 的长连接 | 内存 | 设备在线期间 |
| 场景 | 做菜、开会、翻译等活动上下文，只存轻量状态：滚动摘要、生效的常驻指令、进行中作业的状态 | `agent_scenes` + 内存 | 分钟到小时 |
| 任务 | 一次逻辑请求：召回 → LLM → 结果 | 内存 + `skill_executions`（技能任务） | 秒级，可并发 |
| 作业 | 后台进化作业，由 Pi 在沙箱里执行 | `evolution_jobs` + Pi 会话文件 | 分钟级，持久化 |

用户说“以后做菜时告诉我这个食物含有什么”之后，交互侧只做三件事：识别为学习请求并做可行性预检，立刻口头回应，登记作业。随后这个任务结束，交互 LLM 没有被占用。生成由另一个进程、另一个会话完成。

## 2. 什么时候开新上下文

大多数时候**不需要新开“会话”，只需要新开“任务”**：每个任务共用同一场景，带最近一两轮的摘要，不带旧任务的全文。判断顺序，前几条是确定性规则，不用额外的 LLM 分类：

| 情形 | 处理 |
|---|---|
| 新对象、新问题，没有指代（拿起另一个食物问“这是什么”） | 新任务，同一场景 |
| 有指代或省略（“它再多放点盐”），且距上一轮不久 | 续接同一任务线程 |
| 修改进行中的作业（“也要提示过敏原”） | 不开新上下文；给对应的 Pi 会话追加 `steer`（运行中排队）或 `follow_up`（结束后送达） |
| 询问进度（“学好了吗”） | 直接查作业表回答，不调用 LLM |
| 场景切换（开始开会、出门、关机） | 关闭当前场景（写摘要），新建场景 |
| 空闲超时 | 关闭场景；时间阈值做成配置项，默认值通过实测确定 |
| 上下文接近上限 | 先做滚动摘要压缩，不新开 |

实现建议：最近一两轮在时间窗内一律带上，让主模型自行忽略不相关的部分，比单独加一个分类器更简单、更稳健。

### 新上下文的“种子”

作业开始后，用户后续的对话在新的任务上下文里进行。新上下文必须注入两样东西，否则“也要提示过敏原”这类话没有对象：

1. 当前生效的常驻指令。
2. 一份很短的“进行中作业清单”（作业 ID、标题、状态），从 PostgreSQL 读取。

路由发现用户在谈某个进行中的作业，就把话追加给对应的 Pi 会话；用户用自然语言指代“上次让你学的那个”时，用记忆召回（带 `job:<id>` 标签的语义记录）找到作业，再回 PG 查详情。

## 3. 作业与交互的隔离

- 作业有自己的 Pi 进程与会话，每个作业独立的 `--session-dir` 与 `--name`；不与交互共享上下文。
- 交互任务优先于后台作业：模型额度、并发、限流队列分开；作业走较慢或较便宜的通道。
- 每设备同时进行的作业数做成配置，默认 1（设备少于 10 台）；超出排队。
- 作业期间交互不受影响：Runtime 不在交互线程里等待作业，一切通过状态变更事件通知。

## 4. 场景生命周期与“熏种子”

```text
OPEN ── 空闲超时 / 场景切换 / 设备下线 ──► CLOSING ──► CLOSED
                                         │
                                         └─ 摘要写入用户记忆库（现行熏种子），summary_retained_at 落库
```

- 关闭时不保留常驻的 LLM 上下文，只写一份摘要。以后“恢复”等于新建场景，再靠记忆召回找回摘要（种子生现行），不需要复活旧会话。
- 记忆写入的粒度是会话或逻辑任务：会议纪要在会议结束时写，翻译在会话结束时写摘要，不逐句写。
- Runtime 异常退出时，`agent_scenes` 里仍为 `OPEN` 且超时的场景由启动扫描补写摘要。

## 5. 作业状态与会话持有

```text
QUEUED → GENERATING → TESTING → VERIFYING → READY_FOR_REVIEW → CONFIRMED → CLEANING → CLEANED
              ▲                                   │
              └────────── 用户打回（follow_up） ───┘
      任意活跃状态 → FAILED / ABANDONED；READY_FOR_REVIEW 超时 → EXPIRED
```

| 作业状态 | Pi 会话 | 说明 |
|---|---|---|
| `QUEUED` | 未启动 | 等待并发名额 |
| `GENERATING` / `TESTING` / `VERIFYING` | 活跃 | 沙箱里跑，每个作业一个容器 |
| `READY_FOR_REVIEW` | 保留，空闲 | 技能版本已自动推送为 `TRIAL` 并提醒用户；用户有修改意见则回到 `GENERATING` |
| `CONFIRMED` | 保留到清理开始 | 技能转为 `ACTIVE` |
| `CLEANING` → `CLEANED` | 删除 | 见 `evolution-pipeline-v1.md` 第 10 节 |
| `FAILED` / `ABANDONED` / `EXPIRED` | 到期后清理 | 防止会话无限堆积 |

- **保留期**：未确认作业保留一周（`expires_at = READY_FOR_REVIEW 进入时间 + 7 天`）。到期：版本 `TRIAL → EXPIRED`，作业 `EXPIRED`，会话进入清理；若技能没有已确认版本则暂停（建议，待确认）。
- 确认前保留会话的好处：用户说“不对，还要加过敏原”时，可以在同一个 Pi 会话里接着改，上下文都在；用户的确认或打回也是评测的真值标签。
- Runtime 通过租约（`lease_owner`、`lease_until`）驱动作业；租约过期，另一个实例或重启后的实例可以续跑。

## 6. Pi 会话的记忆与压缩

- Pi 会话内部的记忆不用 Runtime 操心：会话是追加式 JSONL 树，Pi 在接近模型上下文上限时自动压缩。RPC 里可以用 `get_session_stats` 看上下文占用，用 `compact` 手动压缩，用 `set_auto_compaction` 开关自动压缩，用 `get_entries`（带 `since` 游标）读取包括压缩前的完整历史。压缩只影响模型看到的内容，原始记录仍在文件里。
- 压缩是有损的。**需求、验收标准、测试用例必须钉在工作区文件里**（`SPEC.md`、`tests/`、`AGENTS.md`），不能只靠对话记忆。
- 一个作业一个会话，不要让一个会话堆多个互不相关的作业。
- Pi 的自动压缩只管 Pi 会话。Spring Boot 内的交互对话不是 Pi 会话，需要自己的滚动摘要加 Hindsight 召回，不要依赖超长上下文：大窗口通常意味着每轮成本和延迟更高，实时设备上不划算。

## 7. 通知与激活

- 激活不打断正在进行的任务：任务固定使用启动时的版本，新版本只在任务之间切换。
- 提醒要选时机：做菜时手上忙，优先用 HUD 轻提示或在自然停顿时送达（`out.notify` 的 `delivery.whenIdle`），不要在用户操作的当口插话。
- 试用提醒只发一次；用户可以回复“好用 / 稍后 / 别再提示”，对应 `feedback` 消息。

## 8. 示例时间线（做菜场景）

| 时间 | 用户 | 交互任务 | 作业 |
|---|---|---|---|
| t0 | “以后做菜时，告诉我眼前食物含有什么，适不适合我吃” | 任务 A：预检为“能做”，应答，登记作业，结束 | `QUEUED → GENERATING` |
| t1 | 拿起另一个食物：“这是什么” | 任务 B：新任务、同一场景，内置识别照常回答，不阻塞 | `GENERATING` |
| t2 | “也要提示过敏原” | 任务 C：识别为修改作业，向作业追加 `steer` | 吸收新要求 |
| t3 | — | — | 验证通过，`READY_FOR_REVIEW`；版本推送为 `TRIAL` |
| t4 | 听到提醒“新技能可试用” | 在自然停顿时送达，发一次 | 等待确认，保留 7 天 |
| t5 | 再拿起食物，技能自动提示；点“好用” | `skill_executions` 记录反馈 | `CONFIRMED → CLEANING → CLEANED` |
