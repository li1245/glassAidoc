# 里程碑与验收（v0.3）

## 1. 总体方法：先打穿，再加厚

最大的未知数是“自进化闭环能不能跑通”，不是翻译功能。所以先做一条最薄的、每一环都是真的完整链路，再逐个加厚：

> 手机拍一张食物照片问“这是什么”（内置）→ 说“以后做菜时提示食物成分” → 可行性预检 → 登记作业 → Pi 生成 → 沙箱测试 → 自动推送试用 → 再拍一张，技能自动提示 → 点“好用”确认 → 清理会话

三项与硬件无关的资产要先做好：**设备接入规范 v1**、**设备模拟器**、**一致性测试集**。以后自研硬件对着它们实现。

## 2. 里程碑

| 阶段 | 交付 | 验收 |
|---|---|---|
| **M0 契约冻结** | 设备信封与消息类型、能力词表、`SkillManifest` v2、作业状态机；V4–V7 迁移评审后落库；Schema 生成 Kotlin 与 TS 类型 | `contracts/validate.py` 通过；迁移在 PostgreSQL 18 上复跑 `verify_v4_v7.sql` 全部通过 |
| **M1 设备网关与手机端** | 入网接口、WSS 网关、能力注册表；命令行模拟器；Android 客户端（二维码入网、mTLS WSS、能力上报、拍照、语音、显示、播放） | 模拟器与手机都能入网并上报能力；一致性测试第 1–4、7 项通过 |
| **M2 第一个内置功能** | 拍照识别（或语音互译）；会话与任务管理；Hindsight 会话级召回与摘要写入 | 一次拍照得到回答；场景关闭后记忆里有摘要；并发两个任务互不阻塞 |
| **M3 Broker** | 能力目录、dry-run 与模拟后端、统一错误码、资源仲裁骨架；导出 OpenAPI 并生成按设备裁剪的 TS SDK | 用夹具跑通一次能力调用；“拔掉摄像头”后可行性预检给出“做不了” |
| **M4 技能运行器** | 沙箱里的运行器；一个手写的示例技能；V4 迁移落库；技能路由；试用护栏 | 手写技能被路由命中并正确执行；试用技能在冷却内不重复触发 |
| **M5 Pi 进化 Worker** | Pi 沙箱镜像；Kotlin 的 RPC 客户端；作业表与状态机；证据包；可行性预检；单角色生成；沙箱测试；候选登记与试用推送 | **上面的“薄链路”端到端跑通** |
| **M6 评测与清理** | 回放用例、影子运行、用户反馈标签、确认后清理、孤儿扫描、一周过期 | 打回、确认、过期三条路径都走通；清理后会话文件与工作区确实被删除 |
| **M7 加厚** | 测试作者与审查者角色、先单路再并行；会议纪要；传感器接入（模拟曲线、戒指）；沙箱加固（gVisor 或 microVM） | 流水线对比单 agent 的成功率、耗时、成本有数据；沙箱攻防测试通过 |

## 3. 第一批任务（M0 与 M1 起步）

1. 评审并确认 `decision-log.md` 里的待确认项（尤其 D-010、D-016）。
2. 把 `docs/drafts/db/` 的 V4–V7 放入 `db/migration/`，在 PostgreSQL 18 上跑迁移与 `verify_v4_v7.sql`。
3. 用 JSON Schema 生成 Kotlin 与 TS 的契约类型，替换手写的信封与 manifest 类。
4. 建设备网关（WSS）与能力注册表，先用模拟客户端联调。
5. 写命令行模拟器与时间线脚本格式，准备 3–5 个夹具（照片、语音、心率曲线）。
6. 做 Android 客户端的入网（二维码）与能力上报。
7. 做会话与任务管理的骨架，用“睡几十秒再返回”的假作业验证交互不被阻塞。
8. 搭 Pi 沙箱镜像，在本机跑通一次 RPC 对话（不接业务）。

## 4. 测试策略

| 层 | 做法 |
|---|---|
| 契约 | `contracts/validate.py` 进 CI；示例同时覆盖通过、Schema 失败、语义失败三类 |
| 数据库 | `verify_v4_v7.sql` 进 CI，在 PostgreSQL 18 上跑 |
| 协议 | 一致性测试集同时跑命令行模拟器、手机、未来硬件 |
| 能力 | 夹具与 dry-run 保证可重复；故障注入覆盖硬件离线、权限被拒、忙、电量低 |
| 进化 | 评测集对照：单 agent 与多角色流水线的成功率、耗时、token 成本 |
| 安全 | 红队用例（提示注入、沙箱逃逸、Broker 滥用）纳入 CI；渗透测试在 M7 |
| 性能 | 先按“采集 → 传输 → ASR → 翻译 → TTS”拆分延迟预算，再用模拟设备压测，不预设总数 |

## 5. 每个里程碑的完成标准

- 代码与测试合入主分支，`DEV_PROGRESS.md` 记录本阶段改动。
- 对应设计文档按实际实现更新；偏离设计的地方有 ADR。
- 没有已知的高危安全问题；新增的第三方依赖经过审计并固定版本。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| Pi 的模型提供方不能经回环转发使用 Unix 套接字 | M5 之前做原型；备选：容器内回环代理，或把网关挂在受限的内部网络上 |
| Pi 版本变化快，RPC 行为变化 | 镜像固定版本，升级前跑回归；Worker 镜像独立灰度 |
| 沙箱逃逸 | 产品化前升级到 gVisor 或 microVM；沙箱无外部网络 |
| 多 agent 成本高而收益不明 | 默认单路；用评测集证明后才扩大 |
| 手机阶段的结论不适用于自研硬件 | 显示限单行短文本；轻量处理只做编码、抽帧等；协议与硬件无关 |
| 生成的技能质量不稳定 | 静态检查加沙箱测试加影子运行加试用，每层都有验收；用户反馈作为真值 |
| 个人与健康数据合规 | 数据最小化、生物特征单独授权、会话清理、日志脱敏；产品化前做合规评审 |
